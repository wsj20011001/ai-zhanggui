## 1. 三分钟逐镜头

### 0:00–0:15 开场（不念 PPT）

> 「中小餐饮老板每天早上要回答三个问题：今天赚没赚、明天买多少、哪道菜在赔钱。
> 现在的工具给他更多报表，我们给他三个动作。」

### 0:15–0:50 镜头一：驾驶舱 + 拆解（`/admin/ai`）

点首页，只念三条标题：

> 「这是老板打开电脑的第一屏，只有三件事，按轻重缓急排序。
> 第一：昨天营收比同星期低了 31%。第二：基围虾只够 1.5 天。第三：三道菜连续三天没卖出去。」

**动作**：点第一条的「定位原因」。

> 「它没停在『跌了』。营收 = 单数 × 客单价，它把缺口拆开：
> 客流影响多少、客单价影响多少——**结论是人少了，不是点便宜了。**
> 这两个动作的解法完全不同：前者查排班和天气，后者查高单价菜是不是断货。」

### 0:50–1:25 镜头二：让它动手（点库存那条「生成采购单」）

> 「第三条不是提示，是能直接干的。它按未来 7 天预测用量、乘每道菜的配方、
> 减掉现有库存，算出该买几项、多少钱。」

**动作**：进入采购单 → 「确认入库」→ 回库存页看一眼。

> 「库存变了，出入库流水也写了，可追溯到这张单。
> 注意它没有自动下单——关键动作永远留人确认。
> 而且**已入库的单不能一键撤销**，只能走退货。这是我们故意的：真实库存变动不能靠一个按钮抹掉。」

（如果时间紧，跳过回库存页，直接说「库存和流水都更新了」。）

### 1:25–2:00 镜头三：问答 + 证据（`/admin/ai/chat`）

输入：`上周哪道菜毛利最高`

> 「它生成的不是一段话，是一条 SQL。」

展开「查看这条结论用到的 SQL」：

> 「只能查 8 个只读视图，看不到会员手机号，改不了数据，最多 500 行，6 秒超时。
> **所以它不会算错账——因为它不算账，数字是 SQL 算出来的，模型只负责解释。**」

再补一句（这句是加分项）：

> 「而且我们会核对结论里的数字：数量对不上行数、金额不在结果里，就判定为编造，
> 直接换成确定性摘要，再让它看着真实结果重写一遍。」

### 2:00–2:35 镜头四：推演器（`/admin/analytics/simulator`）

> 「AI 给建议，老板不一定信。所以我们让他自己推。」

拖「调价幅度」到 +5%，指着屏幕：

> 「只给 20 道毛利率低于 40% 的菜涨 5 块：月毛利 +9,252，年化 +11.2 万，
> 这些菜销量掉 4%——**销量要再掉 22% 才不划算。**
> 弹性这个假设是他自己调的，不是我们拍的数字。」

### 2:35–3:00 收尾

> 「一句话：别人告诉你哪里亏，我们替你把问题改掉，还能收回、能追查。
> 断网也能用，会员数据不出店。」

## 4. 评委可能追问的 8 个问题

| 问题 | 回答要点（20 秒内） |
|---|---|
| **和现有餐饮 SaaS 有什么区别？** | 他们做「记录」，我们做「决策 + 执行」。收银系统里数据已经全了，缺的是把数据变成动作的那一层。我们不替换收银，长在它上面。 |
| **AI 在哪里？是不是就调了个 API？** | 三处：受控 NL2SQL（白名单 + 五道闸 + 自修复）、规则洞察引擎（6 类检测器，不依赖模型）、可执行工具层（采购/调价/主推 + 撤销）。模型只做意图与措辞。 |
| **本地模型能用吗？数据真不出店？** | 通道代码已打通并用 Mock 验证过（`tests/test_local_channel.py`），本机已装 qwen2.5-3b（Q4，2GB，纯 CPU 约 30 token/s）。实测单次问答 3–12 秒，个别问题 SQL 会写错，所以**日常用云端、断网切本地**。设置页「测试本地模型」会明确告诉你本地起没起；装的时候一条命令 `scripts/setup_local_model.ps1`。**今天演示走云端，本地作为断网兜底。** |
| **你怎么证明这套 AI 靠谱，不是碰巧能跑？** | 固定 12 题评测集，SQL 可执行 12/12、结论一致 12/12、平均 1.2 秒；沙箱越界 8 条全拦；6 个测试套件 12 秒跑完。命令都写在 README，评委可以当场跑。 |
| **模型胡编数字怎么办？** | 三道校验：数量词必须等于行数；金额必须出现在结果集里；不过关就换成确定性摘要并让它重写。刚才演示的每条结论都能点开 SQL 核对。 |
| **宴席那句是 AI 排的吗？** | 排菜是规则引擎（中餐宴席结构 + 预算分配 + 原料校验），AI 负责理解与解释。**自然语言直接成单还没开放**，现在是表单式，这在我们的边界清单里。 |
| **数据是假的吧？** | 是模拟数据但不是编的：按星期效应、节假日、雨天、菜品帕累托分布合成，成本按 38% 成本率校准，生成脚本固定种子可复现。真实门店换自己的库即可，代码不改。 |
| **为什么不用大模型做预测？** | 单店 180 天数据撑不起。用「水平 × 星期因子 × 趋势」，并把回测误差（当前 32%）直接显示在页面上——宁可承认不准，也不美化。 |
| **怎么赚钱 / 怎么推广？** | 单店免费版（离线、只读分析），连锁版按门店数订阅（跨店对比 + 采购协同）。获客靠收银系统存量客户，替换成本几乎为零。 |
| **上线要多久？** | 一周内能接一家店：导入历史订单 → 对齐菜名与配方 → 跑两周看建议采纳率。最难的不是技术，是让老板每天愿意点开那三件事。 |

## 5. 已知边界（被问到就直说，别绕）

1. **自然语言直接下单/排菜没开放**：对话只做查询与分析，业务动作走各自页面。
2. **预测是三层分解，不是深度学习**：单店数据量不够，给区间比给点值诚实。
3. **调价单次 ≤15%**：成本加成算出来的价往往卖不动，差额建议靠改配方补。
4. **采购未考虑供应商起订量与在途**：接入报价单后再补。
5. **局域网 HTTP**：面向店内，外网需加 HTTPS 反代。

> 主动说边界比被问出来强。产业评委见过太多"什么都能做"的项目。
