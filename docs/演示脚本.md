## 1. 三分钟逐镜头

### 0:00–0:20 开场（不要念 PPT）

> 「中小餐饮老板每天早上要回答三个问题：今天赚没赚、明天买多少、哪道菜在赔钱。
> 现在的工具给他更多报表，我们今天想给他三个动作。」

### 0:20–1:00 镜头一：驾驶舱（打开 `/admin/ai`）

指向屏幕，只讲三句：

> 「这是他打开电脑看到的第一屏，只有三件事，按影响金额排序。
> 第一条：昨天营收比同星期低了 20%。第二条：三道菜连续三天没卖出去。
> 第三条：牛腩只够 1.5 天——明天晚市前会断。」

**动作**：点第一条的「定位原因」。

> 「它没有停在『跌了』，而是拆开：营收 = 单数 × 客单价。
> 客流影响 −1,500，客单价影响 −120。所以是人少了，不是点便宜了。
> 这就是老板要的结论，不是图表。」

### 1:00–1:40 镜头二：让 AI 动手（点库存那条的「生成采购单」）

> 「第三条不是提示，是能直接干的。点一下，它按未来 7 天的预测用量、
> 乘以每道菜的配方，减掉现有库存，算出该买 7 种食材、2,757 块。」

**动作**：进入采购单 → 「确认入库」→ 回到库存页刷新。

> 「库存变了，出入库流水也写了。注意：它没有自动下单——关键动作永远留人确认。」

**动作**：回到驾驶舱，点右上角操作记录里的「撤销」。

> 「而且能撤回。每一次动手都有 before 快照，写进操作日志。敢让它动钱，是因为能收回。」

### 1:40–2:20 镜头三：一句话干活（`/admin/ai/chat`）

输入：`明天 8 人宴席，人均 150`

> 「这不是查数，是干活：它按中餐宴席结构（凉菜 15%、热菜 40%、主菜 30%……）
> 排了一套菜，主菜挑贵的撑场面，排除过季和原料不够的，然后一键成单，后厨立刻看到。」

输入：`上个月哪 5 道菜毛利最高`

> 「每个数字都能查。展开这条 SQL——它只能查 8 个语义视图，
> 看不到会员手机号，改不了数据，最多 500 行，6 秒超时。
> 所以它不会算错账，因为它不算账，数字是 SQL 算的，模型只负责解释。」

### 2:20–2:45 镜头四：菜品工程（`/admin/analytics/dishes`）

> 「销量 × 毛利四象限。绿色是明星，红色是瘦狗——卖得多但不赚钱。
> 点调价，它按目标毛利给建议，但单次只涨 15%：算得对不等于卖得动。」

### 2:45–3:00 收尾

> 「一句话：别人告诉你哪里亏，我们替你把问题改掉，还能收回、能追查。
> 断网也能用——本地模型跑在这台机器上，会员数据不出店。」

## 2. 评委可能追问的 6 个问题

| 问题 | 回答要点（20 秒内） |
|---|---|
| **和现有餐饮 SaaS 有什么区别？** | 他们做「记录」，我们做「决策 + 执行」。收银系统里数据已经全了，缺的是把它变成动作的那一层。我们不替换收银，长在它上面。 |
| **AI 在哪里？是不是就调了个 API？** | 三处：受控 NL2SQL（视图白名单 + 五道闸 + 自修复）、规则洞察引擎（6 类检测器，不依赖模型）、可执行工具层（采购/调价/主推 + 撤销）。模型只做意图与措辞。 |
| **数据是假的吧？** | 是模拟数据，但不是编的：按星期效应、节假日、雨天、菜品帕累托分布合成，食材成本按 38% 成本率校准。生成脚本固定随机种子，现场可复现。真实门店换自己的库即可，代码不改。 |
| **模型说错了怎么办？** | 数字不让它说。它只输出 SQL 和一句解读，SQL 先过沙箱；解读必须引用结果里的数字，前端把 SQL 摊开给人看。越界会先自修复一轮，再失败降级成规则查询。 |
| **为什么不用大模型做预测？** | 单店 180 天数据撑不起。用「水平 × 星期因子 × 趋势」，并且把回测误差（22%，含一次异常下滑）直接显示在页面上——宁可承认不准，也不美化。 |
| **怎么赚钱 / 怎么推广？** | 单店免费版（离线、只读分析），连锁版按门店数订阅（跨店对比 + 采购协同）。获客靠收银系统存量客户，替换成本几乎为零。 |

## 3. 兜底方案

| 故障 | 处置 |
|---|---|
| 云端模型超时 | 什么都不用做，8 秒后自动降级本地/规则，界面右上角会变成「规则模式」 |
| 本地模型没起来 | 照样能演：问答走 20 个模板，洞察本来就是规则算的 |
| 页面点乱了 | `reset_demo.py --restore` + 刷新，10 秒恢复 |
| 浏览器崩了 | 换 Edge，`打开管理端.bat` 一键打开 |
| 彻底演不了 | 播 3 分钟录屏，口播照旧 |
