## 版本 1｜30 字（一句话 / 列表页摘要）

AI 掌柜：把餐饮交易数据变成每天 3 个可执行动作的经营 Agent。

---

## 版本 2｜60 字（表格里的"项目方向"）

面向中小餐饮门店，自动发现营收异常、滞销与缺货风险，直接生成采购单、调整菜单、排出宴席；数字由 SQL 计算，每步可审计、可撤销，断网可用。

---

## 版本 3｜100 字（最常用，推荐）

AI 掌柜是面向中小餐饮的经营决策 Agent。每天只给老板 3 件要做的事：营收为什么跌、哪道菜在赔钱、明天该买多少。点一下即可生成采购单、按毛利调价、把滞销菜设为主推，执行前留快照、执行后可撤销。数字全部由 SQL 算出，模型只负责解释，断网也能用。

---

## 版本 4｜200 字

中小餐饮老板每天面对三个问题：今天到底赚没赚、明天该买多少、哪道菜在赔钱。现有工具给他更多报表，却不给结论。

AI 掌柜接在门店已有的收银系统之上，把交易数据折叠成日粒度指标，只输出「今天先做这 3 件事」：营收异常自动拆解成客流影响与客单价影响；滞销菜、缺货食材、折扣失控按影响金额排序；每条都附证据与建议。

与常见经营助手不同，它能直接动手：按预测用量乘配方减库存生成采购单、按目标毛利给出调价建议、把滞销菜设成点餐端主推。每个动作有前置快照与操作日志，可一键撤销。

数字全部由 SQL 计算，模型只能查 8 个只读视图、只做解释，越界即拦截；无网络时自动降级为规则模式，会员数据不出店。

## 版本 5｜400 字（详细版 / 项目文档开头）

**问题**：中小餐饮不缺数据，缺一个能替他做决定的角色。老板手里有六张报表，仍然回答不了三个问题——今天赚没赚、明天买多少、哪道菜在赔钱。采购靠经验，缺货与压货同时发生；207 道菜里只有 107 道算得清成本，卖得越多可能亏得越多。

**方案**：AI 掌柜是长在现有收银系统之上的经营决策 Agent，四层结构：交易底座（点单/收银/会员/BOM/库存）→ 指标层（唯一口径 + 日粒度预聚合 + 8 个只读视图）→ AI 引擎（受控 NL2SQL、6 类规则检测、三层分解预测、可执行工具）→ 决策界面（驾驶舱、问答、洞察、采购单、四象限）。

**它做三件事**：
1. **看得懂**——营收异常自动拆解为「客流影响 + 客单价影响」，告诉老板是人少了还是点便宜了；
2. **算得准**——菜品销量按配方展开成食材用量，减掉现有库存，得出该买多少；预测用「水平 × 星期因子 × 趋势」，并把回测误差直接显示在页面上；
3. **动得了**——生成采购单、按毛利调价（单次≤15%）、滞销菜设为主推，执行前存快照，执行后可撤销、可审计。

**可信设计**：所有数字由 SQL 算出，模型只负责理解问题与组织语言；模型只能访问 8 个语义视图，SQL 需过五道闸（只读连接、白名单、语法校验、强制 LIMIT 与超时、结果上限），越界会先自修复一轮再降级。无 API Key、无外网时自动走规则模式，功能不缺失。

**验证**：已用 180 天、6,803 单的模拟经营数据完成端到端验证，系统自行发现：折扣率从 8.8% 抬到 11.1%、19 道菜连续 3 天零销量、5 种食材可支撑不足 2 天、近 30 天毛利率 57.6%（低于目标 2.4 个点）。20 个页面、8 条越界 SQL、50 项单元测试全部通过。

## 填写时的四条建议

1. **第一句必须能独立成立**。评委可能只读第一句，别用"随着人工智能的快速发展"开头。
2. **少用形容词，多用动词和数字**。"赋能""闭环""抓手"这类词一个都不要；"生成采购单""可撤销""6,803 单"这类具体说法才可信。
3. **数字要标口径**。写"6,803 单"时说明是"180 天模拟经营数据"，宁可不写，也不要让人以为是真实门店数据。
4. **主动写一句边界**。比如"预测不是深度学习，单店 180 天数据撑不起模型"。产业赛道的评委见多了吹牛的，主动认边界反而加分。
