# 技术说明 · AI 掌柜

> 这份文档回答一个问题：**除了调 API，你到底做了什么？**
> 每条结论都对应仓库里的文件和可复现的数字，评委会可以直接核。

---

## 1. 一句话定位

我们不是"给餐饮系统加一个聊天框"，而是**把大模型放进一条不能出错的决策链路里**：
模型只负责"理解问题"和"组织语言"，所有数字由 SQL 与确定性算法产出，
所有动作都留快照、可撤销、可审计。

---

## 2. 四个自研点（对比"简单 API 调用"）

### 2.1 受控 NL2SQL：让模型查数，但不给它改数的能力

| 普通做法 | 我们的做法 |
|---|---|
| 把建表语句丢给模型，让它自由写 SQL | 只暴露 **8 个语义视图**，模型看不到原始表 |
| 执行前扫一遍关键字黑名单 | **五道闸**：只读连接 → 视图白名单 → 语法校验 → 强制 LIMIT/超时 → 结果上限 |
| SQL 报错就直接失败 | 捕获拒绝原因，**带错误信息让模型自修复一轮**，再失败降级规则 |

实现：`ai/sandbox.py`（五道闸）、`ai/nl2sql.py`（提示词、自修复、降级）

关键判断：**黑名单永远会被绕过**，所以真正的安全放在数据库层——
`PRAGMA query_only=ON` 从底层拒绝写操作，视图白名单让它连敏感表名都看不到。

### 2.2 结论级数字校验：大模型最危险的错误不是 SQL 写错

这是我们踩到的真实坑，也是最有说服力的一段。

在接入真实模型（DeepSeek）后，同一个问题出现了三种错误：

| 场景 | SQL 查到的 | 模型写的 |
|---|---|---|
| 库存预警 | 9 种食材 | "共 **6** 种" |
| 牛腩库存 | 2.8 斤 | "3.2 **kg**" |
| 毛利最高 | 辣椒炒肉 7858.8 元 | "**招牌鸡**，3200 元" |

SQL 没错、沙箱没拦、表格也没错，**错在结论**。老板不会去数，评委会。

所以我们加了服务端校验（`ai/nl2sql.py::_check_insight`）：

1. **数量词校验**：「N 种/道/条」必须等于返回行数或去重值数；
2. **金额校验**：结论里 ≥1000 或带小数的数字，必须能在结果集（单元格、列合计、行数）里找到，日期/天数/百分比豁免；
3. **兜底 + 重写**：不通过就换成确定性摘要（`查询返回 9 行，最靠前的石斑鱼：库存 0.96 斤，预警值 1.11 斤`），再让模型**看着真实结果重写一句**，重写完再过一遍校验。

修复后同一批问题的输出全部与表格一致。这条链路是**可被评委当场验证的**：随便问一句，点开 SQL，对着表核。

### 2.3 规则洞察引擎：不依赖模型的经营判断

`analytics/insights.py` 里有 6 个检测器：营收异常、滞销菜品、毛利预警、库存风险、折扣失控、会员流失。

设计要点：
- **同星期基线**而不是"昨天"：餐饮周一和周六不可比，拿昨天当基线会天天误报；
- 营收异常拆成「客流影响 + 客单价影响」的加法分解，直接回答"是人少了还是点便宜了"；
- 每个洞察都带 `evidence`（指标、当前值、基线、阈值、SQL），可追溯到明细。

**这层完全不调模型**——断网、无 Key、模型欠费，它照常工作。这是"AI 不可用时不至于变成废物"的底线设计。

### 2.4 三层分解预测 + 滚动回测

`analytics/metrics.py::_fit_forecast`

```
预测值 = 水平 × 星期因子 × 趋势
水平 = 近 14 天均值
星期因子 = 各星期均值 ÷ 总体均值
趋势 = 近 14 天最小二乘斜率，限幅 ±3%/天（防单日爆单带飞）
```

为什么不用深度学习：单店 180 天数据撑不起，给区间比给点值诚实。
**回测用滚动一步预测**（`_rolling_mape`）而不是留出最后 7 天——
留出法如果刚好碰上异常周，MAPE 会被放大到 90%+，看起来像模型坏了。
当前回测误差 22%（含一次刻意植入的营收下滑周），这个数字**直接显示在页面上**。

## 3. 动作层：让 AI"动手"，但保证能收回

`ai/tools.py`

| 机制 | 实现 |
|---|---|
| 可撤销 | 执行前把 `before` 快照写进 `ai_actions`，一键恢复 |
| 可审计 | 同时写 `op_logs`（谁、何时、改了什么） |
| 有边界 | 调价单次 ≤15%，采购单先生成草稿、人工确认才入库 |
| 幂等 | 采购入库、CSV 导入都按业务键去重，重复执行不产生副作用 |
| 不可撤的地方 | **已入库的采购单不能一键撤销**，只能走退货——真实库存变动不许被按钮抹掉 |

这是刻意的不对称设计：AI 可以快，但不能把一个真实发生的库存变动"撤回"。

## 4. 技术选型与代价（主动说明我们放弃了什么）

| 决策 | 备选 | 为什么这么选 | 代价 |
|---|---|---|---|
| 只用 Flask + waitress | FastAPI / Django | 要能打包成 EXE 在没装环境的门店电脑上跑 | 没有异步生态 |
| 不用 numpy/pandas | pandas 做分析 | 门店电脑不是服务器，启动速度和体积优先 | 预测要手写最小二乘 |
| SQLite + WAL | PostgreSQL | 单店并发 20 路足够，零运维 | 多门店要迁移 |
| 自建语义视图，不用向量库 | RAG / Text2SQL Agent | 结构化问题用 SQL 更准、更可解释 | 开放式问题答不了 |
| 规则洞察 + 模型解释 | 全交给模型 | 洞察必须可复现、可审计 | 覆盖不了长尾场景 |

## 6. 架构决策记录（ADR 摘要）

| # | 决策 | 理由 |
|---|---|---|
| 1 | 模型只做意图与措辞，不做计算 | 数字错一次，整个系统就失去信任 |
| 2 | 只读视图作为模型的能力边界 | 安全不能依赖提示词 |
| 3 | 预聚合 `daily_facts` 而非实时扫明细 | 180 天看板从秒级降到百毫秒 |
| 4 | 洞察用规则、不用模型 | 可复现、可审计、断网可用 |
| 5 | 动作必须可撤销 | 敢让它动钱的前提 |
| 6 | 三级降级：本地 → 云端 → 规则 | 门店网络和预算都不可控 |

## 7. 已知不足（写在材料里，比被问出来强）

1. 对话只做查询分析，**没有开放自然语言直接下单**；业务动作走各自页面，人工确认。
2. 预测是统计分解，不是时序深度模型；节假日因子靠硬编码日历。
3. 采购未考虑供应商起订量与在途库存。
4. 多门店、权限体系未做（字段已预留设计，未实现）。
